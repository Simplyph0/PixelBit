# Changelog

What changed in each version, newest first. The release notes on the
[Releases](https://github.com/Simplyph0/PixelBit/releases) page start with the
matching section from this file. Add your changes under **Unreleased**; when a
version is tagged, rename that heading to the tag (for example `## v4.3`) and start
a new **Unreleased** section above it. Earlier versions are described in their
release notes.

## Unreleased

- **New: Checkers** (game 16): English draughts with compulsory captures and multiple jumps. Vs the computer at five levels (VERY EASY, random, to SUPER HARD, 4 s a move) or a friend on a second console. Same four-button controls as Chess.
- **New: Minesweeper** (game 15): 16 x 7 field, 12 to 30 mines by difficulty, first cell always safe. Up opens (or chords), Down flags, Left/Right run along the rows.
- **Menu:** 20 tiles; VIDEOS, CHAT and SETTINGS move up two. Saved scores and settings keep working. The settings keep "options seen" for up to 21 games (bits 16 to 20 sit in the flags byte, so the EEPROM layout is unchanged).
- **Tests:** checkers perft to depth 8, rules and AI; a two-console checkers game over a lossy radio; Minesweeper rules.

## v4.5

Chess, much easier Tic-Tac-Toe, and a faster build.

- **New: Chess**, the tile after Connect 4 (game 15). Full rules: castling, en passant, promotion, check, checkmate, stalemate and the draws (three-fold repetition, 50 moves, too few pieces, 400 half moves). Play the computer at five levels, VERY EASY (almost random) to SUPER HARD (5 seconds a move), or a friend on a second console (2 PLAYER, then HOST GAME and JOIN GAME). You are White first and the sides swap each game. A win scores 3 and a draw 1, times the level.
- **Chess with four buttons:** Left/Right step through the pieces that can move, Up picks, Left/Right step through where it can go, Up moves, Down goes back. A pawn on the last rank asks what it becomes. A flashing frame is check.
- **Pieces are easy to tell apart:** each has its own 7x7 picture, White is drawn light and Black dark on a lit square, and a **PIECES** setting switches to the letters P N B R Q K.
- **Chess inside:** `chessengine.cpp` has no Arduino code, so the PC tests run exactly what the console runs. It costs about 12 KB of flash and 0.6 KB of permanent RAM; the 2.4 KB move list exists only during a game and the 4.6 KB search workspace only while the computer thinks. The host decides on two consoles and resends lost moves.
- **Changed: Tic-Tac-Toe is much easier at every level** (players found even EASY too hard). EASY plays at random; NORMAL, HARD and EXPERT take wins and blocks only some of the time; INSANE is unchanged and never loses. A careful player now beats EASY in about 90% of rounds, NORMAL 93%, HARD 67% and EXPERT 30%.
- **Fixed: the frog vanished on logs and cars in Frogger.** It is now drawn by inverting what is behind it, so it shows on everything.
- **New: a one-page printable quick start**, `docs/PixelBit-QuickStart.pdf` (black and white). `docs/make_quickstart.py` rebuilds it (needs LibreOffice).
- **Menu:** Chess is game 14, so VIDEOS, CHAT and SETTINGS move up one (18 tiles; SETTINGS is still last). Saved scores and settings keep working.
- **Faster builds and tests:** the firmware sources are compiled once and shared by the emulator and every test (a clean build takes about 1m15s locally). Update tests compile only the one file that differs, Tic-Tac-Toe plays fewer rounds (78s to 5s), and the tests run side by side. On GitHub the tests and the real firmware compile now run in parallel (the Arduino core is cached), and the release waits for both.
- **Tests:** chess rules against the standard perft counts, checkmate, stalemate, draws, castling, en passant and under-promotion; the AI always plays a legal move, finds a mate in one from MEDIUM up and gets stronger with each level; a two-console test plays through the buttons over a radio losing 10% of packets and both consoles must end in the same position. The Tic-Tac-Toe test now fails if the easy levels are not easy, a level is easier than the one below it, or INSANE ever loses. Frogger has a contrast check on logs and cars.
- README: shorter wording throughout, plus chess (gallery, game table, controls, a Chess section) and the new Tic-Tac-Toe levels.

## v4.4

Chat between consoles, a settings menu on the console, and a Wi-Fi page you start from that menu.

- **New: CHAT.** A tile after VIDEOS sends ready-made messages to another console over ESP-NOW: `LET'S PLAY <game>` (the game list comes from the game table, so new games appear by themselves), `BEAT MY SCORE IN <game>` with your best score, and ten short phrases (`WANNA PLAY?`, `REMATCH?`, `GOOD GAME!`, `NICE ONE!`, `YES!`, `NO THANKS`, `MAYBE LATER`, `GIVE ME A MINUTE`, `HELLO!`, `BYE!`). Send to one console, a saved contact, a console that answered a ping (`NEAR`), or everyone. A message to one console is acknowledged, so the sender sees DELIVERED or NO REPLY. An inbox keeps the last 8 messages; Right answers one. Messages are authenticated with the link secret, repeats are dropped, and they are not encrypted (the README says so).
- **New: the notification blip.** A round dot flashes in the top right corner when a message is unread (fast for four seconds, then a slow pulse), on top of any game, menu or video. It sits in a black disc so it shows on bright pictures, and it is drawn in `updateDisplay()` and taken off the buffer again, so no screen needs to know about it. A message that arrives while the screen is off turns it back on.
- **New: SETTINGS, the last tile of the menu.** BRIGHTNESS (five steps, kept), SCREEN OFF (never, 1, 2 or 5 minutes without a button; any button wakes it and that press does nothing else; a playing video, an update and the Wi-Fi page keep the screen on), CHAT ON/OFF (default ON: the console listens in the background, and the radio is handed to the Wi-Fi pages and the two-console games and taken back afterwards), WI-FI PAGE, UPDATE FIRMWARE, RESET SCORES, RESET OPTIONS, SHOW INTRO (the welcome and tour play again on the next boot), FACTORY RESET (scores, game settings, brightness, screen off, chat, contacts and videos, then the console restarts as a new one) and ABOUT (version, this console's id, build date, button layout, free memory). The resets need a hold of Right (2 seconds, 3 for the factory reset), and the hold only starts after Right has been let go, so a long press on the list cannot erase anything.
- **Changed: the Wi-Fi page (save backup and chat contacts) starts from SETTINGS > WI-FI PAGE.** The hidden button code (Left, Left, Right, Right, Up, Up, Left, Right, then hold Up) and the double-tap of Up that stopped it are gone, along with their `SECRET_*` and `SYNC_DOUBLE_*` settings in `config.h` and the separate "sync" state in the game manager. **Left** stops the page.
- **New: chat contacts on the Wi-Fi page.** Type a console's 5-letter id and a name of 1 to 10 characters (so it always fits the screen), up to 8, kept in the EEPROM. The page shows this console's own id, which is also in SETTINGS > ABOUT and on the CHAT screen.
- **Changed: the list menus** (SETTINGS, the VIDEOS clip list and the test mode list) scroll with **Up/Down**; **Right** selects and **Left** goes back or leaves. The same goes for the upload page, the settings confirmations and the screens inside SETTINGS. Playing a video and the menu carousel work as before.
- **Changed: the console-to-console firmware update moved from test mode into SETTINGS**, so it no longer needs the hidden test-mode combo. Test mode keeps its other pages.
- The menu has 17 tiles (CHAT is the 16th, SETTINGS the 17th). `MAX_GAMES` is 17; the settings still keep a 16-bit "options seen" mask, so only games 0 to 15 can have options. EEPROM map: scores at 0, game settings at 128, device settings (brightness, screen off, chat; 8 bytes) at 200, chat contacts at 220, the test-mode scratch area at 400. Every block has a checksum, and a console without the new ones uses the defaults (HIGH brightness, never off, chat on).
- Internals: `GameLink` gets a chat packet type that is handled in every state, `begin()` starts from a clean slate when the radio is already on, and `linkIdFromText()`/`linkIdToText()`. `Game` has three small hooks (`menuNote`, `keepsScreenOn`, `skipPresent`) and `GameManager` has `resetGameOptions()`, `factoryReset()` and `showIntroNextBoot()`. The emulator's display stub accepts `ssd1306_command` (brightness and power are not emulated) and its `String` accepts `+=` of a string.
- Tests: `chat_test` and `chat_check.py` (ids, aliases, contacts and their EEPROM round trip, message text, two consoles over a radio losing 0% and 20% of the packets: ping, delivered, sent, no reply, repeats dropped, and chat and a two-console session sharing the radio); `persistence_check.py` also covers SHOW INTRO, FACTORY RESET and the accidental-hold case. The video check presses LEFT three times to reach VIDEOS.
- `tools/flasher/pixelbit_flasher.py` is a point-and-click firmware flasher for Linux, macOS and Windows (several consoles at once, 460800 baud, chip erase off by default, finds esptool from pipx, tells you which group to join when the port is not yours).
- **Fixed: the console-to-console firmware update crashed the receiving console.** On real consoles the transfer sat at 0% on both screens, the sender then gave up with a stalled-transfer message, and the receiver restarted a few seconds later with its old firmware. The USB serial log of the receiver showed `Panic core_esp8266_main.cpp:191 __yield` right after the fifth chunk arrived, with this call chain: `sendAck()` called `poll()`, which handled the next queued chunk, which called `sendAck()` again, and so on. When the radio is still sending the previous packet, `sendAck()` waits for it, and it used to wait by calling `poll()`. The sender sends a burst of 8 chunks, so the receiver nested one level deeper for each queued chunk, each level costing a few hundred bytes of the 4 KB stack, until the stack overflowed. `GameLink::poll()` now does nothing when it is already running, so a packet handler can wait for the radio without handling more packets from inside itself. Checked on two real consoles with different flash chips: a 470 KB image went over in about 10 seconds (2,449 chunks, one packet lost and resent), the receiver checked the hash and restarted into the new firmware.
- Why the tests did not catch it: the simulated radio in the emulator and the test programs finishes a send at once, so a console never has to wait for the radio. The crash needs a real radio that is still busy when the next packet is ready.
- **New: a failed update says on the screen how far it got.** A stalled transfer shows `tx12 ack3 lost9` on the sender (chunk packets sent, acknowledgements received, packets the radio reported lost) and `got 40 bad 0 at 38` on the receiver (chunk packets received, chunk packets rejected, chunk written up to). "Cannot start" and "Writing the image failed" show the updater's own error code. The README has a new section, "If an update fails", explaining every failure screen and these numbers.
- **New: update debugging over USB serial.** Build with `UPDATE_DEBUG` set to 1 (in `config.h`, or `-DUPDATE_DEBUG=1`) and the update and the link log, at 115200 baud: the offer, the accept, the first chunks, a line every 100 chunks, every refused packet and why (wrong tag, wrong size, repeated sequence number), radio send errors, and the updater's result and free memory. It is off in normal builds and costs nothing then.
- Fixed: a receiver counted every chunk packet as proof that the sender was alive, even one it rejected, which could hide a stalled transfer. Only a valid chunk counts now, so a receiver that keeps getting bad packets gives up after the usual 10 seconds.
- Emulator and tests: the emulator's updater stand-in has `getError()` like the real one, so the new failure screens build there too.
- README: the update section now gives a realistic transfer time, lists the failure screens, explains how to capture a serial log, and the troubleshooting list has an entry for an update that sticks at 0%. The firmware layout notes explain the rule that `poll()` ignores calls from inside itself.
- Every release now has a second file, `PixelBit-<version>-flipped.bin`: the same firmware built with `FLIPPED_BUTTONS` set to 1 for a board built upside down. `FLIPPED_BUTTONS` in `config.h` can now be overridden by the compiler (`-DFLIPPED_BUTTONS=1`), and the release notes list a checksum for each file. The button layout is part of the firmware, so a console-to-console update copies the sender's layout: update between consoles built the same way round.
- `pbv.py` handles GIFs properly: animated GIF, WebP and APNG files convert like any video, and their transparent parts are laid over a solid colour first (black by default, `--background white` to change). Before, ffmpeg dropped the transparency and whatever colour was hidden under a transparent pixel came out as the picture, so a sticker-style GIF could turn into a solid block. Other inputs convert exactly as before.

## v4.3

- Changed: the button layout is set in `config.h` again (`FLIPPED_BUTTONS`, `0` by default; `1` for a board turned over) and is fixed when the firmware is built. The v4.2 run-time layout is gone: the first-boot tour no longer learns it and test mode has no LAYOUT page. A console that saved a layout under v4.2 now follows `config.h`; the two settings bits it used are ignored.
- The video player no longer keeps its two picture buffers (about 2 KB) in RAM while it is not playing; they are taken when a clip opens. The clip list's JSON buffer (about 0.7 KB) moved off permanent RAM too.
- The firmware update tests use fixed version numbers (4.2 receiver, 4.3 newer sender, 4.0 older sender), so raising `OS_VERSION` no longer changes what they check.
- New: **VIDEOS** in the menu plays black and white videos with no sound. Pick a clip from the list (Up plays, Left/Right pick, Down leaves), pause with Up, jump 5 seconds with Left/Right, Down goes back to the list.
- Videos are uploaded over Wi-Fi from the last entry of the list (the console makes a password-protected network and a web page that also lists and deletes clips). They live in the console's flash file system (LittleFS): about 1.9 MB for up to 16 clips with the default `4MB (FS:2MB OTA:~1019KB)` flash setting, which the release builds now name explicitly. Keep the same Flash Size on every console you update from or to: where the file system sits is part of the firmware, so an update that moves it erases the videos.
- New converter `tools/video/pbv.py` (Windows, macOS, Linux; needs Python 3 and ffmpeg) turns any video into a `.pbv`. `--pixel 1` to `4` trades detail for how easy the picture is to see and for file size, and there are dither, contrast, brightness, invert, fit and fps options.
- Every console ships with one demo clip inside the firmware, copied into the file system the first time the player opens (the one in the repo is a test pattern; `pbv.py --embed` replaces it).
- The menu shows "NO SOUND" under VIDEOS where games show the best score.
- Tests: the video converter and the console's decoder are checked against each other, and the real player runs in the emulator.
- The emulator and the tests now run on Linux, macOS and Windows (MinGW-w64/MSYS2). Build them with CMake, see `tools/README.md`.
- GitHub Actions runs the tests on all three systems before every release build.
- The emulator opens its SDL window by default on Windows and macOS, and its `--bridge` option takes a Windows COM port or a macOS `/dev/cu.*` device.
- The tests are much quicker (about one minute instead of six): fewer Tic-Tac-Toe games for the AI check, the two-console games play side by side, and the firmware update test runs on a faster simulated clock.
- The first-boot saved-data test is now a Python script (`persistence_check.py`) instead of a shell script, so it runs on Windows too.
- Release notes now start with the matching section of this changelog.
